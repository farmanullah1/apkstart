ApkStart User Manual and Troubleshooting Guide

Version: v0.6.2 · Platform: Windows 10/11 x64 · Updated: 2026-11-19 ApkStart is an Android app runner for Windows: Android apps install, appear on the desktop and open on double-click just like native Windows software. This manual first explains how to use it, then works through problems by symptom, with steps you can follow. Every step matches a real button or menu in the app.

1. ApkStart in 30 seconds

Desktop icon (the real app icon, .lnk)
      │ double-click
      ▼
ApkStart.exe --launch <package>
      │ Android runtime not running? -> start it automatically (Android 14 emulator, bundled or downloaded once)
      ▼
Open the app through the launch entry the system resolves (not the main Activity hardcoded in the APK)
      ▼
Emulator window = app window (renamed, re-iconed, portrait aspect, centred fullscreen)

What makes it different

  • 🖱️ Double-click an .apk to install: after registering the file association in Explorer, double-clicking an APK parses it, installs it and creates a desktop icon.
  • 🧩 One desktop icon per app: the icon is extracted offline from inside the APK; double-clicking it goes straight into the app.
  • 🪟 An app is a window: native rendering, fullscreen filling the screen height and centred; windowed mode can be dragged and resized, and each app remembers its own size.
  • 🔍 Findable from Windows: shortcuts on both the desktop and the Start menu (Programs\ApkStart\).
  • 📁 Shared data: %USERPROFILE%\ApkStartShared ↔ Android's /sdcard/ApkStartShared, synced both ways.
  • 🪶 Self-contained runtime: no dependency on MuMu, LDPlayer, WSA or any other emulator installed on your machine.
Note: this is an early-stage project, maintained in the author's spare time, open source, free and ad-free. Problems happen; this manual exists for exactly that.

2. Install and first launch

2.1 Pick the right build

Both sources carry the same content; Gitee is usually faster in mainland China:

  • GitHub: github.com/RoutineMiku/apkstart/releases
  • Gitee: gitee.com/daily-miku/apkstart/releases (much faster direct connection)
BuildFile nameWhen to choose it
Store versionApkStart_<four-part version>_x64.msixInstall from the Microsoft Store. Ships the full runtime, works offline after install, updates handled by the Store
Full portableApkStart-v*-win64-full.zip (~830 MB, ~1.3 GB extracted)No installation and no waiting for downloads: extract and run, runtime fully included
InstallerApkStart-v*-Setup.exe (~1.3 GB)You want desktop/Start menu shortcuts and an uninstall entry
Light portableApkStart-v*-win64-portable.zip (96 MiB, ~227 MB extracted)Just trying it out; the runtime is downloaded on first launch
⚠️ Always use the latest version (currently 0.6.2). Older versions (0.5.x and earlier) either have no bundled runtime and fetch/download 1.5 GB on every launch, or default to the embedded window — which is exactly where "slow, will not open, a window with a rotate button appears" comes from. If you upgraded from an older version, check that the desktop shortcut points at the new program directory.

2.2 What happens on first launch

  1. (Light build only) download the runtime: adb, Android Emulator and the Android 14 system image, measured at 10+ MB/s from the official source, 8 chunked threads with resume. The full and Store builds skip this step.
  2. Extract the image for the first time: the xz image expands into %APPDATA%\apkstart\system-images (~20 seconds, one time only).
  3. Create /data for the first time: ApkStart builds its own ext4 user data with encryption and SELinux labels (the official image only contains a 1 MB placeholder).
  4. Automatic boot: after that, opening an app is just one am start — about 23 seconds cold, about 10 seconds from a snapshot.
A slow first launch is normal: it is a one-off cost. Everything after that is instant.

3. Everyday use

3.1 Install an app

Any of three ways:

  • Double-click the APK file (register the association first: Settings -> System Integration -> Associate .apk files);
  • Choose "Install app" in the main window;
  • Command line: ApkStart.exe <path\to.apk>.

Split packages (.apks / .xapk) are supported (they use install-multiple automatically). Desktop and Start menu shortcuts are created after installing.

3.2 Open an app

Just double-click its desktop icon. All apps share one runtime, so a second app starts almost instantly.

3.3 Windows and display

The runtime restarts only on the launch where "panel orientation and app orientation disagree" (about 40 seconds; the title bar shows a hint). Apps with the same orientation open instantly afterwards.

%USERPROFILE%\ApkStartShared on the host and /sdcard/ApkStartShared inside Android sync both ways within seconds. Entry point: Settings -> Integration & Files -> Shared files (you can "Sync now" or "Open folder").

Settings -> Updates & About -> Check for updates, or right-click the tray icon -> Check for updates. The updater measures and picks the fastest source (GitHub / Gitee / mirror), downloads in parallel chunks and switches sources on failure. Updating never loses the runtime, installed apps or snapshots.

4. Three core concepts (the key to reading errors)

Most "weird problems" come down to one of these three things. A minute here makes everything else easier.

4.1 Runtime / system image

ApkStart does not emulate an "empty Android": it boots a complete Android 14 system image as the base. 0.6.2 has one general image (Google Play x86_64) that runs both x86 and ARM apps — no more separate "AOSP image / compatibility image" pair.

  • Image missing / corrupt / incompatible with old user data -> boot failure, stuck at boot, repeated restarts.
  • User data (/data) is a thin difference layer; the system image is shared by the whole machine.

4.2 Hardware acceleration

For the emulator to be fast, it needs CPU virtualization. On Windows there are only two routes:

RouteWhat it isNeeds adminNeeds a reboot
WHPXThe built-in Windows feature "Windows Hypervisor Platform" (HypervisorPlatform)Yes, when enabling itYes
AEHDGoogle's own kernel driverYes, when installing itNo

It still runs without acceleration (pure software emulation, TCG), but booting takes minutes and frames drop — that is "slow", not "failed to start". ApkStart falls back automatically and retries up to four parameter sets ("render backend -> acceleration -> memory/cold boot").

Do not confuse VirtualMachinePlatform (used by WSL2) with the acceleration switch. The emulator needs HypervisorPlatform. With only the former, emulator -accel-check still reports unavailable.

4.3 ARM translation layer

Most Chinese Android apps ship only ARM native libraries (arm64-v8a / armeabi-v7a) while the system image is x86_64 — a "translation layer" is needed to translate ARM instructions for the x86 CPU. The 0.6.2 general image includes the new ndk_translation layer, so installing ARM apps normally needs no setup at all.

  • The first time an ARM app appears without the translation layer in place, ApkStart adds the compatibility image and restarts the runtime to retry (see 6.3).
  • Old images (API 30) are incompatible with the new layer (ByteDance apps trigger DoBadTrampoline SIGABRT); the Android 14 image fixes this.

5. First step with any problem: self-check and auto-detect

Before digging through this manual, let the app check for you — it fixes most problems automatically.

5.1 Machine self-check · automatic configuration

Where: Settings -> Diagnostics & Repair -> Start self-check

  • What it checks: whether CPU virtualization (VT-x/SVM) is on, whether Hyper-V / Hypervisor Platform is available, GPU/VRAM/driver, memory, OS version, emulator -accel-check and the AEHD driver.
  • "Apply recommended settings" writes the safe values (memory / cores / render resolution / quality / force software emulation without acceleration) and saves them as a local driver profile that is applied automatically from then on.
  • Results are graded ok / warn (works but should be improved) / bad (will not run as-is). Each has a colour and an explanation.

Only two things need you personally:

  • BIOS virtualization: reboot into the BIOS -> enable Intel VT-x / AMD SVM -> Enabled (the app cannot do this for you).
  • Windows features / acceleration driver: see 6.1.

5.2 Auto-detect (automatic debug)

Where: Settings -> Diagnostics & Repair -> "Auto-detect · Smart diagnostics"

Every 10 minutes it inspects the machine in the background, lists problems in six groups, and each item can be fixed in one click (restart the runtime, clear locks, kill orphan processes, drop the snapshot, free disk space, reset the Android network, ...). It re-checks after fixing:

GroupProblems covered
RuntimeThe real reason the last start failed, a stuck boot, leftover lock files, orphan emulator processes, an empty snapshot shell, missing hardware acceleration
Device connectionadb unauthorized, offline, runtime running but adb cannot see the device
StorageFree disk space, data partition configuration not matching reality, an unwritable shared folder
SettingsScreen orientation conflicting with the physical panel, auto fullscreen not applying in detached-window mode
Network / logsNo network inside Android, unreachable download sources, errors in the latest log
Two principles: a failed probe is never treated as a problem (if the state cannot be read it reports "unknown" rather than guessing); and the same old problem is not reported again and again.

5.3 Export a diagnostic report

Where: Settings -> Diagnostics & Repair -> Export diagnostic report (or the button of the same name on the System Integration page)

The report is plain text and contains the machine configuration, the startup parameters chosen automatically, the log and the diagnosis. Attaching it to a bug report speeds up triage enormously.

5.4 Built-in manual and automatic tutorials

Since 0.6.2 this manual is built into the app: the "?" button in the title bar and "Open manual" under Settings -> About both open it, with search, scrolling and print/save to PDF. It opens directly at the section relevant to the current problem.

Auto-detect and repair also bring the tutorial to you:

  • When auto-detect finds a problem, a "Tutorial" button appears next to it that jumps straight to the matching section;
  • For hardware acceleration, install failures, the ARM translation layer, adb authorization and missing sound, the tutorial opens automatically when the automatic repair fails, so you do not have to come looking;
  • A given tutorial auto-opens only once per run, so it never keeps interrupting you.
To open it manually: the ? button in the title bar. To stop the automatic pop-ups temporarily, turn off notifications in the auto-detect settings; tutorials still open from the "Tutorial" button on a problem.

6. Troubleshooting

6.1 "Hardware acceleration not enabled" / slow boot

Symptom: settings or diagnostics say "no hardware acceleration" or "hardware acceleration unavailable"; booting takes minutes and frames drop.

First, note: this is usually "slow", not "will not open". ApkStart already falls back to software emulation. Acceleration is only needed for smoothness.

What to do depends on your build:

  • Installer / portable: Settings -> Diagnostics & Repair -> Machine self-check -> find "Hardware acceleration not enabled" -> click Fix. A UAC prompt appears once and WHPX is enabled automatically; if that fails (unsupported, or you declined), the AEHD driver is installed instead.
  • Microsoft Store (MSIX): Store apps cannot elevate themselves, so "Fix" opens the "Turn Windows features on or off" dialog:

1. Tick "Windows Hypervisor Platform" (HypervisorPlatform); 2. Click OK and reboot once.

You can also run this in an administrator PowerShell:

``powershell dism /online /enable-feature /featurename:HypervisorPlatform /all /norestart dism /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart ``

Two traps: (1) do not enable only VirtualMachinePlatform — that is not the acceleration the emulator needs; (2) if VT-x/SVM is disabled in the BIOS, enable it there first (see 5.1), otherwise the Windows feature does nothing. If your graphics driver is more than three years old, update it from the vendor's site; ApkStart never installs drivers automatically (a wrong driver is worse). Some old GPUs and integrated graphics need a compatibility patch: Settings -> Diagnostics & Repair -> Drivers · Compatibility patches.

6.2 Install failed (INSTALL_FAILED_*)

Symptom: installing an app fails; the message usually starts with "Install failed:" and ends with an INSTALL_* error code.

ApkStart translates the raw English error into readable text. Use the table below:

Error codeMeaningWhat to do
INSTALL_FAILED_NO_MATCHING_ABISThe app ships only ARM libraries and the current image has no ARM translation layerUsually automatic: ApkStart switches to the compatibility image and retries. See 6.3
INSTALL_FAILED_OLDER_SDKThe app requires a newer Android versionNeeds a newer image; the current one is Android 14 (API 34), so this is rare
INSTALL_PARSE_FAILED_NO_CERTIFICATESThe APK has no valid signatureThe APK is corrupt or unofficial; get it again
INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES / INSTALL_FAILED_UPDATE_INCOMPATIBLESignature differs from the installed versionUninstall the old version first
INSTALL_FAILED_VERSION_DOWNGRADEA newer version is already installedDowngrading is not allowed; install a newer version or uninstall first
INSTALL_FAILED_INSUFFICIENT_STORAGENot enough disk space in the runtimeFree up space, or move the runtime data directory to a drive with room (Settings -> System Integration)

INSTALL_FAILED_INVALID_URIThe APK path contains special or non-ASCII charactersMove the APK to a pure-ASCII path and retry
INSTALL_FAILED_ALREADY_EXISTSThe same package exists with a different signatureUninstall it first

If the error is raw English outside this table, export a diagnostic report (5.3) and report it.

6.3 No ARM translation layer / ARM apps will not install or crash

Symptom: installing reports INSTALL_FAILED_NO_MATCHING_ABIS with text like "the app only provides ARM native libraries ... the current system image has no ARM translation layer"; or the app installs but crashes immediately, with DoBadTrampoline, libndk_translation, UnsatisfiedLinkError or ...so not found in the log.

How it works: 0.6.2 uses one general Android 14 image that supports x86 and ARM with the translation layer included. Older versions needed a manual image switch; the "general compatibility image (managed automatically)" switch now exists only for old configurations and normally never needs touching.

What ApkStart does automatically:

  1. If installing reports NO_MATCHING_ABIS it switches to the compatibility image -> restarts the runtime -> reinstalls installed apps from the local APK backups -> installs again (log: "Switching to the compatibility image and restarting the runtime...").
  2. If the app crashes on start and the log clearly points at the ARM translation layer (e.g. DoBadTrampoline), it switches to the Android 14 compatibility image and retries (log: "ARM translation layer crash detected; switching to the compatibility image automatically...").

What you can do:

  • Be patient: switching images restarts the runtime, about 40 seconds to a minute, with a notice window in between.
  • Check the image is in place: Settings -> General & Install -> Runtime, look at "general compatibility image (managed automatically)"; if it shows not downloaded, click "Download compatibility image" (~1.5 GB) and restart the runtime afterwards.
  • Still crashing: a few apps have deeper anti-emulator checks (verifying real sensors, the baseband, etc.) and cannot run in an emulator. The app says so plainly; that is a limitation, not a fault.

What if you see a red "Install failed" together with text saying "retrying after switching to the compatibility image"?

That was a display bug in older versions: the image file was on disk, but after reuse of an old runtime without the translation layer the retry was skipped and the failure reported, while the message still claimed a retry was running. You are not on the latest code; upgrade to the newest 0.6.2 build (the build this manual matches probes the runtime's real translation support before installing instead of just checking for the file; NO_MATCHING_ABIS always triggers switch + restart + snapshot drop + reinstall, and a second failure is reported honestly). Install again after upgrading.

Measured: the app "Hongguo Free Drama" (com.phoenix.read, arm64-v8a-only) installs, reaches its feed and plays video on the Android 14 image with the new translation layer. In the current runtime ro.product.cpu.abilist = x86_64,arm64-v8a, so the layer is active.

6.4 adb unauthorized (allow USB debugging)

Symptom: diagnostics report "adb unauthorized" or "Android debug authorization incomplete", adb devices shows unauthorized, and the app never starts.

The right steps, in order:

  1. Look for an emulator window showing the "Allow USB debugging?" dialog — tap Allow in that window and tick "Always allow from this computer"; it will not ask again.
  2. If the window does not respond or never appears: Settings -> Runtime -> Reset Android data / Clear Android data and retry (installed apps are erased, the APK files remain and are reinstalled automatically; the system itself is untouched).
⚠️ Never delete %USERPROFILE%\.android\adbkey. Measured to be counterproductive: Android only writes a new public key when the adb_keys file is absent; with a new private key the old public key on the device still applies, the two do not match and authorization never succeeds.
Command-line check: ApkStart's adb server runs on the dedicated port 5044 (completely separate from your own 5037): ``powershell $env:ANDROID_ADB_SERVER_PORT = 5044 adb devices # should list emulator-5554 ` Do not run adb connect` against port 5555 — Play images show the "Allow USB debugging" dialog on top of the app, which looks like the program is broken.

6.5 Tapping the icon does nothing / endless spinner / window with a rotate button

These almost always point at the launch entry or window hosting. Work through the steps below.

① Confirm you are running the new program

  • Look at the start of %APPDATA%\ApkStart\logs\app.log: it should say start v0.6.2. If it says v0.5.x, the desktop or Start menu shortcut still points at the old directory.
  • Older versions (0.5.x) have no bundled runtime and default to the embedded window -> "very slow plus a shell window with a rotate button". Switch to 0.6.2 and point the shortcut at the new ApkStart.exe.

② Expect the boot time

About 23-48 seconds cold and about 50 seconds for an orientation restart are normal. During that time tapping the icon looks like "nothing happened" although it is booting in the background. Do not tap repeatedly: extra taps let a second instance adopt the emulator, and the first instance's cleanup can shut it down, causing a failure (0.6.2 has an owner.pid guard, but queued waiting still looks like nothing happening). Tap once and wait.

③ The native window was not attached -> fallback to the embedded window with a rotate button

If the log shows attach failed or emu:0, the window proxy could not find the emulator window and the app fell back to embedded mode (the shell window with a title bar and rotate button you are seeing).

  • Most likely when launched through a directory junction or a non-standard path; 0.6.2 resolves real paths before matching. If it still happens, report it with the log.

④ Reset Android data (last resort)

Settings -> General & Install -> Reset Android data (it asks for confirmation). Installed apps and data are erased while the system itself, the app list and automatic reinstalling on open are kept. Use it for a corrupt data partition or anything caused by /data failing to mount.

6.7 No sound / very quiet

Symptom: video and notification sounds in Android apps are silent; or other Windows software has sound but only ApkStart's apps do not.

First separate the cases: if the system itself has no sound, fix Windows audio first; only if just ApkStart's apps are silent should you follow the steps below.

  1. Windows volume and output device: click the taskbar volume icon, make sure nothing is muted, the volume is not 0 and the output device is the headset/speakers you are using. Open Volume Mixer and check that the ApkStart / Android runtime row is not individually muted or pulled to 0.
  2. In-app volume: some apps set media volume to 0 on first run; raise it in the app's own settings or with the Android volume keys. Bilibili, Douyin and others can also mute autoplay independently inside the app.
  3. ApkStart's sound switch: Settings -> General & Install -> Android app audio must be ticked. Auto-detect in 0.6.2 checks this item and reports it under Settings -> Diagnostics & Repair with a one-click "Fix". Restart the Android runtime afterwards (the switch decides whether the emulator starts with -no-audio, so changing it while running has no immediate effect).
  4. Windows audio service: press Win+R, type services.msc, find Windows Audio and make sure it is "Running" with startup type "Automatic". If it was disabled, start it; auto-detect also catches this. As administrator you can run net start Audiosrv.
  5. Bluetooth headset / multiple output devices: after switching to a Bluetooth headset Windows sometimes does not move already-running programs over. Disconnect and reconnect the headset, or restart the Android runtime.
  6. Still silent: export a diagnostic report (Settings -> Diagnostics & Repair -> Export diagnostic report) and report it; the report includes the sound switch and audio service state, which immediately tells config, service and app issues apart.
When automatic repair fails the app opens this section for you. If you turned off auto-detect notifications, open it from the "Tutorial" button on the problem or the ? button in the title bar.

9. Getting help and feedback

When reporting a problem, include these three things — they speed up triage enormously:

  1. Diagnostic report: Settings -> Diagnostics & Repair -> Export diagnostic report;
  2. The last 20 lines of app.log: %APPDATA%\ApkStart\logs\app.log;
  3. Your version and build: e.g. "Store 0.6.2" or "Full portable 0.6.2".
